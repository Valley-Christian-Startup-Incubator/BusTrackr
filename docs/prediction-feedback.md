# Prediction feedback

Riders report from either web view. Simple shows "The bus is here" (the camera missed a bus) and, within 30 minutes of a detection, "The bus isn't here" (the detection was a false alarm). The second asks the rider to confirm they were already waiting at the stop before the detection. The map view's camera panel shows "At Fehren" and "At campus" while the feed is current, and "Looks wrong" while an estimate is shown.

## Record

The worker appends one JSON object per line to `FEEDBACK_FILE` (default `<ALERT_STATE_FILE>.feedback.jsonl`). It never rewrites the file.

```json
{"id":"…uuid…","receivedAt":"2026-11-09T15:08:00.000Z","verdict":"arrived","view":"map","stop":"fehren",
 "collector":{"commit":"f15017a","release":"f15017a8c2d1…"},
 "prediction":{"model":"learned-runs-v1","status":"scheduled","runId":"run-1512","nextCrossingAt":"…","quality":{…},…}}
```

- `verdict` is `arrived` (the rider saw the bus at that time), `false-alarm` (the rider was waiting at the stop before the last detection and no bus came) or `wrong` (the shown estimate looked wrong).
- `stop` is `fehren`, `campus`, or `null` for Simple view reports. The estimator learns trip length only from `arrived` reports with a stop, which come from the map view.
- `view` is `simple` or `map`. Simple riders saw only the time since the last detection, not an estimate.
- `prediction` is the server's own `/api/shuttle` prediction when the report arrived, not a copy sent by the client. `model` names the estimator and `quality` is its backtest score at that moment.
- `collector.commit` is the worker's `BUSTRACKR_COMMIT`. It stays `null` until the worker is deployed from git (issue #24). `collector.release` is the web app's `bustrackr-release` meta tag, written by the deploy controller.
- `id` is generated by the browser, once per verdict. A retried request with the same id is stored once, across restarts too.

`POST /api/feedback` takes `{"id","verdict","view","stop","release"}` as JSON. It is rate limited to 10 requests per minute per client IP and accepts the same browser origins as the rest of the API.

## Reading it

`arrived` reports against `estimatedArrivalAt` or `nextCrossingAt` give a direct error per model. `arrived` reports while `status` is `unknown` or `unconfigured` point to buses the camera or the learned runs missed. Arrival reports with a stop are the only training input besides the camera, and only for trip length. A rider can be wrong, so each day gets one vote and outlying days are dropped.

```sh
jq -c 'select(.verdict=="arrived" and .prediction.status=="estimated")
  | {model:.prediction.model, errorSeconds:((.receivedAt|sub("\\.\\d+Z$";"Z")|fromdate)-(.prediction.estimatedArrivalAt|sub("\\.\\d+Z$";"Z")|fromdate))}' .data/feedback.jsonl
```
