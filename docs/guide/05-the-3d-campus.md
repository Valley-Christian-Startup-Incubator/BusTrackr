# 5. The 3D campus

Map mode doesn't use Google Maps or Mapbox. It's a Three.js reconstruction of the shuttle corridor and the Valley Christian campus, built from public data and hand-authored landmarks. It needs no API token, and every asset ships from this repo.

The first commit, on September 9, 2026, used Cesium with streamed Google tiles. Within days it was replaced by a local Three.js scene. Cesium code stays in git history, but nothing imports it now.

## What the scene is made of

| Layer | Source | Where it lives |
| --- | --- | --- |
| Terrain | USGS 3DEP elevation, blended with lidar ground points around campus | `public/local-scene/elevation.json`, `public/terrain/` |
| Route and roads | OpenStreetMap, with estimated carriageway widths, lane paint, and curbs | `public/data/routes.json`, `public/local-scene/road-profiles.json` |
| Buildings | OSM footprints with inferred pitched or flat roofs | `public/local-scene/footprints.json`, `roadside-roofs.json` |
| Main campus roofs | Authored by hand, with heights guided by lidar | `src/local/building-shell.ts`, `src/local/campus.ts` |
| Trees | 602 instance placements, kept off buildings, fields, and the route | `public/local-scene/landscape.json` |
| Materials | Original synthetic textures, generated with an image tool | `public/local-scene/*-albedo.webp` |
| The bus | An original model built in code | `scripts/build-bus.ts` → `public/models/valley-bus.glb` |

Aerial imagery exists in the repo, but only as an offline reference for placing things. The renderer never loads it.

Each data file has a neighboring `*-source.md` that records where the data came from and what's approximate. Read `roads-source.md` and `buildings-source.md` before you "fix" a road width or a roof height. The current value may be a documented estimate.

Point-cloud roofs were tried and rejected. Meshes built straight from lidar showed stepped artifacts up close. `scripts/build-campus-roofs.py` still generates them for reference, but nothing loads them.

## Regenerating data

The `public/` data is generated by scripts, then committed. A few examples:

```sh
npm run build:landscape          # side streets, parcels, terrain boundary, tree placements
npm run build:corridor           # route corridor polygons, after route data changes
python3 scripts/build-road-profiles.py
```

The lidar scripts need a Python environment at `.venv-lidar/` with numpy, scipy, laspy, and pyproj. The [main README](../../README.md#regenerate-assets) lists every command.

`npm run build` runs six scene checks before TypeScript and Vite: road profiles, local scene, road contact, building surfaces, modeled terrain, and parking layout. A broken asset fails the build, not the rider's phone.

## Performance budget

The scene targets 30 FPS and does a lot to hit it:

- Geometry is merged by material, so the GPU gets fewer draw calls.
- Trees are instanced in spatial cells. A cell switches to simpler foliage once the camera is more than 240 meters from its bounding sphere.
- Only buildings fully inside the clipped corridor render.
- Pixel ratio is capped at 1 on phones and 1.4 on desktop.
- A paused scene renders only when the view changes. A hidden tab renders nothing.
- Startup fetches run in parallel. A request stalled for 20 seconds shows a retry button.

Every frame, the `.world` element's `data-diagnostics` attribute holds FPS, draw calls, triangles, and rendered building and tree counts. [`performance.md`](../performance.md) has the measurements. Each one comes from a desktop browser at phone size. None is a real-phone benchmark, and that doc says so on every table.

## Getting the scene into a phone

The native app runs the scene in a WebView. A WebView normally loads a URL, but the app has to work with no website at all. So `scripts/build-mobile-scene.mjs`:

1. reads every scene asset (terrain JSON, footprints, textures, the bus GLB),
2. base64-encodes each one into a `data:` URI,
3. bundles `src/mobile-scene.ts` with esbuild, swapping `src/local/asset-urls.ts` for a version that returns those data URIs,
4. writes one self-contained HTML document into `mobile/src/map/scene.generated.json`.

`SceneMap.tsx` loads that HTML with `baseUrl: 'about:blank'`. Nothing goes over the network.

That generated file is about 14 MB, and it used to be committed. Every rewrite added 14 MB to every clone and fetch, and it eventually stalled the deploy host's `git fetch` (chapter 6 has that story). Commit `3c3488c` added it to `.gitignore`. Mobile scripts that bundle or typecheck now regenerate it first, and EAS builds generate it in `eas-build-post-install`.

## Talking across the WebView wall

The native app and the scene speak a small typed protocol, `mobile/src/map/protocol.ts`:

- Native to scene: `injectJavaScript` calls `window.BusTrackrScene.receive(command)`. Commands are `state` (the marker), `camera` (a preset view), `orbit`, and `zoom`.
- Scene to native: `ReactNativeWebView.postMessage` sends `ready` or `error`.

Both sides validate with zod. A malformed command is dropped silently.

The marker carries its own expiry time. `sceneState()` sets `expiresAt` to the earliest of:

- now + 45 seconds,
- the prediction's `generatedAt` + 45 seconds,
- the feed's `lastCheckedAt` + 120 seconds,
- the estimated arrival time.

The scene sets a timer and removes the marker when it expires, even if the native side never sends another message. If the JavaScript bridge stalls, the bus disappears instead of freezing at its last position.

## Grill session

**Q1.** Someone opens a PR that loads the NAIP aerial photo as the ground texture "because it looks more real". What's the problem?

<details><summary>Answer</summary>

The renderer deliberately never loads aerial imagery. It's an offline reference for placing things. The scene uses meter-scaled synthetic materials whose detail doesn't depend on the photo's resolution. The PR would also add a large download to every phone. Read `public/local-scene/README.md` and the `*-source.md` files before changing what the renderer loads.

</details>

**Q2.** The native app's 3D map works in airplane mode. How?

<details><summary>Answer</summary>

`build-mobile-scene.mjs` inlines every asset as a base64 `data:` URI inside one HTML document. The WebView loads that HTML from the app bundle with `baseUrl: 'about:blank'`. The scene makes no network requests. The feed does, so the marker won't update offline, but the campus renders.

</details>

**Q3.** The phone's JavaScript thread freezes for a minute while an estimate is showing. What happens to the bus marker inside the WebView?

<details><summary>Answer</summary>

It disappears within 45 seconds at most. `expiresAt` was capped at now + 45 seconds when native sent it. The scene's own timer clears the marker at that time without waiting for another message. A marker the app can't refresh is worse than no marker.

</details>

**Q4.** You add a new texture and the web map shows it, but the native app throws `Asset not packaged`. Why?

<details><summary>Answer</summary>

`build-mobile-scene.mjs` packages only the paths in its `paths` list. The mobile build replaces `assetUrl()` with a lookup into that list, which throws on anything missing. Add the new file to `paths` and rebuild with `npm run check:mobile-scene`.

</details>

**Q5.** You clone the repo, `cd mobile`, and run `npx tsc` directly. It fails with "Cannot find module './scene.generated.json'". Is the repo broken?

<details><summary>Answer</summary>

No. The file is generated and ignored by git. `npm run typecheck` and the other mobile scripts build it first, and they need the root dependencies installed (`npm ci` at the repo root) because the generator uses esbuild from there. Run the npm script, not the bare tool.

</details>

**Q6.** `performance.md` shows 30.0 FPS on a 390 × 844 viewport. Can you tell a teacher the app runs at 30 FPS on an iPhone?

<details><summary>Answer</summary>

No. Those numbers come from a desktop Chromium window sized like a phone. A real phone has a different GPU, thermal limits, and a WebView instead of Chrome. The doc says outright that physical-device performance remains unverified.

</details>
